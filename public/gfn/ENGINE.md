## GeForce revision 2 — Epic sign-in loading repair

The latest published upstream packages were checked on 2026-10-03 and match the
existing hashes above. Main has an export-declaration rewriter change, but there
is no published replacement release or confirmed Epic-specific fix to substitute.

`lib/geforce/controller-lifecycle.js` and the vendoring script repair controller
startup races in this build. A restarted worker now claims `/gfn/browse/` requests,
waits up to eight seconds for the correct launcher, and queues an early popup's
transport handshake. Registration wakes waiting requests without refetching or
replaying OAuth POSTs. Revive messages contain registered controller IDs, so a
live port is not replaced and the old five-second guard cannot suppress recovery.
This follows the mechanism discussed in upstream pull request 211 and additionally
handles Kkeep's custom prefix and early `initRemoteTransport` messages.

- https://github.com/MercuryWorkshop/scramjet/pull/211
- Reproduction and regression coverage: `tests/proxy-geforce-lifecycle.test.mjs`
- GeForce now loads `/gfn/runtime.js?v=2`, generated by
  `scripts/build-geforce-runtime.mjs`; the original apps' runtime is unchanged.
- The revision check replaces only an older `/gfn/` worker. No shared cookies,
  main-app registrations or saved user data are cleared.
- GeForce authentication/CDN failures log only hostname, HTTP status, method and
  a coarse failure stage. URLs, query strings, credentials and bodies are not logged.

Verified locally: cold-worker module requests, concurrent navigation, queued popup
ports, OAuth POST preservation, cancellation, orphan timeout, separate launchers,
and old-worker migration. Epic's unproxied public form rendered in the test browser.
The hosted proxy's complete Epic account-linking flow and iPad gameplay have not
been verified: the managed local preview has no secure service-worker context.

## GeForce revision 3 — one identity for each JavaScript module

Epic's existing error reports revealed React error 321 during account linking.
The bundled rewriter reproduces a module identity mismatch: an HTML module entry
uses the document's `$io` origin, while a static import of the same entry uses
the CDN origin. Browsers treat those as separate modules, which can initialize
two React runtimes. Dynamic imports already use the document origin.

The vendoring patch retains the initiator in fetch metadata and supplies it to
the pinned WASM's static-import origin bridge during synchronous rewriting.
The original CDN base still resolves relative imports. The local value is scoped
inside the GeForce bundle and restored in `finally`; this does not change native
URL behavior, authentication URLs, callbacks, cookies, CAPTCHA, or other apps.
Both string and byte input paths now produce the same module URL as HTML and
dynamic imports. Source-map offsets are generated for the corrected URL.

- Implementation: `lib/geforce/module-identity.js` and the vendoring script.
- Regression: `tests/proxy-geforce-modules.test.mjs` fails on the original engine
  and checks matching module identities, relative URLs and rewrite isolation.
- A native Chrome ESM fixture using the generated query metadata confirmed two
  module initializations with the original build, and one shared instance with
  this patch. This verifies module loading, not completed Epic account linking.
- GeForce's engine/runtime/worker revision is 3; existing sessions are retained.
- `worker/geforce-diagnostics.ts` projects only allowlisted error categories and
  numeric script positions from already-relayed Epic reports. It excludes raw
  messages, request data, credentials, URL queries and account identifiers.
